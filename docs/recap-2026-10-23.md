## Fase 2.1 — Simulador Python

El simulador de `simulator/simulate_radar.py` utiliza `config/room.json` como configuración común del espacio, el radar y la simulación.

| Parámetro | Valor |
| --- | --- |
| Habitación | 4 m de ancho × 5 m de largo |
| Modelo configurado | HLK-LD2450 |
| Posición provisional del radar | X = 2 m, Y = 0,6 m, Z = 0,75 m |
| Rotación configurada | 0° |
| Objetivos | Hasta 3 |
| Intervalo final | 100 ms, equivalente a una frecuencia nominal de 10 Hz |

La posición del radar es provisional; no representa una instalación física calibrada. La altura Z se conserva en la configuración, pero el procesamiento revisado trabaja sobre el plano X/Y.

Las tramas contienen coordenadas locales `x_mm` y `y_mm`, en milímetros respecto al radar, y `speed_cm_s`, en centímetros por segundo. Esta velocidad es radial: indica acercamiento o alejamiento respecto al radar, no las componentes de velocidad sobre los ejes. En el simulador revisado, el signo positivo corresponde al alejamiento.

El formato JSON incluye `schema_version`, `source`, `radar_id`, `timestamp` y la lista `targets`; cada objetivo se identifica por un `slot`. Los timestamps del simulador se generan en UTC, con precisión de milisegundos. El modo independiente emite un objeto JSON por línea.

Durante la jornada se ajustó `update_interval_ms` de 200 a 100: se pasó de 5 Hz nominales a 10 Hz nominales. Se comunicó una verificación aproximada de 10 Hz. El archivo de configuración inspeccionado confirma el valor final de 100 ms; esta revisión no vuelve a medir la frecuencia ni aporta una estadística de latencia.

## Fase 2.2 — Backend FastAPI

El backend de `backend/app/main.py` carga la configuración y reutiliza directamente la función Python `make_frame` del simulador. No necesita consumir la salida de otra terminal ni iniciar el simulador como un proceso separado.

### Arquitectura

```text
config/room.json
       |
       v
Simulador Python: medidas locales + timestamp
       |
       v
FastAPI: validación y transformación de coordenadas
       |
       v
StateHub: último estado válido
       |                         |
       v                         v
HTTP /api/state              WebSocket /ws
instantánea                  actualizaciones
                                 |
                                 v
                      Próxima fase: HTML/SVG
```

Una tarea productora genera las tramas cuando la simulación está habilitada. El backend valida los datos antes de sustituir el último estado válido. El código revisado comprueba, entre otros aspectos, el esquema, el identificador del radar, la fecha con zona horaria, los slots únicos y el límite de objetivos.

Cada cliente WebSocket tiene una cola de tamaño uno. Si un cliente consume lentamente, se conserva el estado más reciente en lugar de acumular todos los mensajes. Por tanto, este mecanismo distribuye el estado actual; no es un registro histórico de cada medida.

### Endpoints

| Ruta | Función |
| --- | --- |
| `GET /health` | Informa del estado del servicio y de si la simulación está habilitada; el código devuelve 503 si la tarea productora termina inesperadamente. |
| `GET /api/room` | Devuelve la configuración del espacio, el radar y la simulación. |
| `GET /api/state` | Devuelve la última trama procesada, con coordenadas globales. |
| `WebSocket /ws` | Envía el estado disponible y las actualizaciones posteriores. |
| `/docs` | Interfaz Swagger para consultar y probar los endpoints HTTP. |

`/ws` es una salida del estado, no una entrada de medidas del radar. Con la simulación deshabilitada y sin otra adquisición, el estado inicial es `null`.

### Coordenadas y unidades

El backend convierte milímetros a metros, aplica la rotación del radar y después su traslación:

```text
x = x_mm / 1000
y = y_mm / 1000

X_global = radar_x + cos(theta)·x - sin(theta)·y
Y_global = radar_y + sin(theta)·x + cos(theta)·y

speed_m_s = speed_cm_s / 100
```

Con rotación 0° y el radar en (2; 0,6) m, una medida local de (1200; 2400) mm corresponde a (3,2; 3,0) m globales. Es un ejemplo explicativo, no una captura de una prueba.

El campo `inside_room` indica si el punto está dentro de los límites de la habitación, incluidos los bordes. El backend mantiene también los puntos exteriores, marcándolos como tales. La velocidad convertida a m/s sigue siendo radial.

## Principales aprendizajes

- Una configuración compartida evita que simulador, backend y futura interfaz utilicen dimensiones o posiciones diferentes.
- Separar coordenadas locales y globales, con unidades explícitas, evita errores de escala y de ubicación.
- Un intervalo de 100 ms implica 10 Hz nominales. La frecuencia observada puede variar por planificación del sistema, procesamiento y transporte.
- HTTP permite consultar una instantánea; WebSocket permite recibir cambios sin repetir peticiones.
- Validar antes de publicar protege el último estado correcto frente a tramas inválidas.
- Un commit guarda los archivos preparados y un push publica commits. Los archivos untracked quedan fuera de ambos hasta incorporarlos.
- La presencia de pruebas en el proyecto y su ejecución satisfactoria son evidencias distintas.

## Limitaciones y asuntos pendientes

La adquisición sigue siendo simulada: estas comprobaciones no validan un radar físico, su instalación, su ruido, sus pérdidas de seguimiento ni su conexión con otros equipos. Los slots del simulador no demuestran identificación persistente de personas.

El estado se conserva en memoria y no hay un histórico en el flujo descrito. La geometría es bidimensional y la posición del radar necesita confirmación cuando exista la instalación real. La cadencia aproximada observada no constituye una garantía de tiempo real estricto.

La arquitectura revisada debe ejecutarse con un único worker para compartir el mismo simulador y estado entre clientes; varios procesos tendrían estados independientes. Todavía falta la representación visual HTML/SVG. La lectura de código realizada para este documento no sustituye las pruebas de ejecución, de integración con hardware o de despliegue.
